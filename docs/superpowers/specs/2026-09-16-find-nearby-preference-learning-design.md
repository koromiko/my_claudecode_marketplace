# find-nearby 偏好學習機制重新設計

日期：2026-09-16
狀態：已核准，待實作
取代：`2026-09-05-find-nearby-design.md` 中的「Step 0.5 偏好檔」與「Step 11 回饋階段」兩節

## 問題

現行機制把偏好存成一個扁平的 markdown 檔，四個等級桶（反感／強偏好／弱偏好／未定），
每條是一句自由文字，靠「2 次獨立目擊」升級，每桶上限 8 條。它的隱含假設是
**偏好跨店種通用**。這個假設在 2026-09-16 的小倉執行被證偽：

- 強偏好「自家製造・自家調達」（3/3）是從自由が丘的雜貨店與咖啡廳、埼玉的烏龍麵店
  與義大利麵店、下関的漁船直捕居酒屋學來的。
- 本次套用到精釀啤酒與角打ち。命中最強的兩家（林田酒店的自家酒藏、飛来haku 的
  酒藏直採）被排在第 1、第 2，**使用者一家都沒選**。
- 使用者實際選的三家共有的軸是「營業時段寬鬆、白天就開」與「可先試飲再買瓶裝」，
  這兩個軸在現行資料結構裡**從來沒有欄位可以承載**。

同一次執行還暴露第二個問題：強偏好「獨立店／獨棟路面店，而非連鎖品牌或商場樓層內
的分店」被用來把 MELKED 小倉駅ナカ店下修到 △，而使用者照樣選了它。那半段規則當場
失效。

第三個問題最安靜：**每次執行丟掉的訊號比留下的多。** 偏好檔只記 👍 與 👎 的兩三家，
但真正的訓練訊號是「我們排的順序 vs 使用者選的」。本次把飛来haku 排第 1（未選）、
MELKED 排第 8（選了），這個倒置是「我們哪裡想錯了」的直接證據，現行機制連記都沒記。
10 家展示過的候選，有 9 家的資訊當場蒸發。

## 目標

1. 偏好的適用範圍能隨店種變化，而且不需要人工維護一張店種表。
2. 每次目擊盡可能多存結構化欄位，讓「軸」可以事後被發現，而不是當下就被壓縮成一句話。
3. 保留「一個候選被刷掉，使用者要看得見、而且能糾正」這個性質。
4. 減少 skill 需要維護的帳：升級運算、條目上限、合併與汰換全部消失。

## 非目標

- 不做跨使用者的偏好共享。
- 不做數值權重或學習率；推論由 LLM 在執行當下做，不訓練任何模型。
- 不在本次做店種側寫卡快取（見「延後項目」）。

## 架構

兩個檔案，權責分開（原先考慮的第三個 `hard-rules.md` 併入 `preferences.md`，不另立檔）：

| 檔案 | 誰寫 | 角色 |
|---|---|---|
| `~/.config/trip-notes/sightings.jsonl` | 只有 skill 寫，append-only | 機器讀的目擊紀錄 |
| `~/.config/trip-notes/preferences.md` | **只有使用者寫**，skill 從此不再改 | 使用者親口說的話 |

權威順序：**使用者親口說的 > 從目擊紀錄推論出來的。**

`preferences.md` 的角色轉變是本設計的關鍵一步。它現行那四個桶其實是 LLM 從 16 筆
目擊蒸餾出來的，而那 16 筆會被 backfill 進 jsonl，**所以桶是可重現的衍生物、不是
原始資料**。轉成純人工檔後，「使用者手改的內容必須存活」這條性質不再依賴
「skill 只能用 Edit」的紀律，而是由「skill 根本不寫這個檔」保證。

skill 讀 `preferences.md` 時，把整份內容當作使用者本人的陳述，優先於任何推論；
它不再解析區塊標題，也不再要求特定格式。

## 記錄結構

每筆記錄 = 一家**展示過的**候選 × 一次執行。JSONL，一行一筆。

```jsonc
{
  // ── 執行脈絡（同一次執行的每筆都相同）
  "run_id": "2026-09-16-kokura-craftbeer",   // <run_date>-<地點 slug>-<主題 slug>
  "run_date": "2026-09-16",
  "target_date": "2026-09-19",
  "region": "福岡県北九州市小倉北区",
  "origin": "小倉駅",
  "request": "北九州市小倉精釀啤酒或清酒，車站走路可到 (20分鐘)，日期 9/19",
  "queries": ["クラフトビール", "ビアバー", "日本酒", "地酒 立ち飲み", "角打ち"],
  "mode": "WALK",
  "max_min": 20,

  // ── Google 免費就有的
  "place_id": "ChIJ...",
  "name": "酒の中村園魚町店 角打ちなかむらえん",
  "type": "酒店",
  "pool_hits": 3,
  "matched_queries": ["クラフトビール", "日本酒", "角打ち"],
  "travel_min": 7,
  "rating": 4.7,
  "reviews": 61,
  "status": "OPERATIONAL",
  "open_from": "13:00",
  "close_at": "21:00",
  "hours_span_h": 8,
  "closed_days": [],
  "irregular_closure": true,
  "amenities": {},

  // ── 我們的判斷（用來測自己的誤差）
  "rank_shown": 3,
  "tier": "首選",

  // ── 使用者回饋
  "verdict": "👍",          // "👍" | "👎" | null（展示過但未標記）

  // ── 只有首選層有；缺就是缺，不得補值
  "research": {
    "independent": true,
    "chain": false,
    "in_mall": false,
    "founded": null,
    "own_production": false,
    "price_band": "¥1,100/飲み比べ",
    "seating": "立ち飲み+テーブル",
    "has_website": true,
    "instagram_state": "age_restricted",
    "official_info_conflict": false
  }
}
```

兩個欄位需要特別說明：

**`matched_queries`** — 由 Step 3 既有的 pool 合併結果直接得出：本次每個
`pool-*.json` 都對應一個查詢詞，該檔含有此 `place_id` 就把該詞收進來。
不需要額外 API 呼叫，也不需要 LLM 判斷。記錄本次哪幾個查詢詞獨立命中了這家店。這些是**使用者自己的
用詞**，拿來分群比 Google 的 `type` 更貼近使用者腦中的分類。`pool_hits` 已經是它的
計數，但計數丟掉了詞本身，而詞才是分群要用的東西。

**`verdict: null`** — 展示過但沒被選的候選也要寫。它們是弱負面訊號，且只有配上
`rank_shown` 才能看出「我們排第 1 的使用者沒選」。代價是 log 成長約 5 倍（每次約
10 筆而非 2–3 筆）；20 次執行約 200 筆，仍遠在單次 context 可讀範圍內。

`hours_span_h`、`open_from`、`close_at`、`closed_days`、`irregular_closure` 由
`hours` 物件推導。推導在寫入時做一次，不要求讀取端每次重算。

## Scoring agent 契約（Step 5）

brief 改成強制三步，順序不得顛倒：

1. **分群。** 用 `type` 重疊**或** `matched_queries` 重疊，切出與本次相關的歷史目擊。
   必須先寫出這群有幾筆、包含哪些店。
2. **在群內找軸。** 每條軸都要附計數，例如
   「`hours_span_h ≥ 8` 的 5 家裡 3 家 👍；`< 4` 的 4 家 0 家 👍」。
   **沒有計數的軸不准使用。**
3. **才排序**，並在「排序依據」印出用了哪些軸與各自計數。

第 3 步的輸出是對抗「每次推論不一致」的唯一手段。漂移不會消失，但會變得看得見。

`rank_shown` 與 `verdict` 的落差要被主動使用：agent 應該找出歷史上「排得高但沒被選」
與「排得低卻被選」的案例，並說明本次如何避免重蹈。

## 刷掉權

證據門檻與現行機制相同，只是改成從資料計算而非人工記帳。

- 相關群 **< 5 筆**目擊 → **完全沒有刷掉權**，且必須在筆記寫
  「此店種僅 N 筆目擊，推論薄弱」並退回接近中性的排序（條件符合度 → rating）。
- 要刷掉一個候選，需要同時滿足：
  - 該群內 **≥ 2 筆 👎** 共有該特徵，
  - 來自 **≥ 2 次不同執行**（同一次執行注意到的兩項特徵只算 1 次），
  - **任何一群都沒有**帶同一特徵的 👍（矛盾證據永久禁止刷掉）。
- 通過後，筆記的「已篩掉的候選」仍要逐條寫明：
  `〇〇屋 — 本次推論「X」（證據：2 筆 👎 / 0 筆 👍）。若這條推錯了，告訴我。`

矛盾證據那條規則在 2026-09-16 一次執行中就救了兩次（「單一嗜好專門店」被手打うどん
大井戸 的 👍 鎖住；「商場樓層內分店」被 MELKED 的 👍 當場推翻），成本低、效果明確，
改寫時必須保留。

## Step 11 回饋階段

兩個 `AskUserQuestion` 問題照舊（「哪幾家想去」「哪幾家一看就不要」，皆 multiSelect）。
之後只做一件事：**append 約 10 筆記錄**（本次展示過的每一家）。

移除：2/2 升級運算、每區 8 條上限、合併與汰換、`最後更新：` 行維護。

回報那行從「偏好檔改了什麼」改為
「已記錄 10 筆目擊（3 👍 / 1 👎 / 6 未標記）」。

使用者略過不答仍是合法結果：此時 `verdict` 全部寫 `null`，記錄照寫——
展示過這件事本身有資訊。

## Backfill

現有 `preferences.md`「證據紀錄」的 16 筆補成稀疏記錄，只填
`name` / `run_date` / `region` / `verdict` 與原本那句散文（放進 `note` 欄），
標 `legacy: true`。**缺的欄位留空，不得回頭猜測或重新查詢。**

`preferences.md` 本身保持原狀不動；使用者若想清掉那四個桶，那是使用者自己的決定。

## 錯誤處理

- `sightings.jsonl` 不存在 → 中性模式，一行告知（與現行相同）。
- 個別行 JSON 壞掉 → 跳過，回報跳過筆數，**絕不中止整次執行**。
- 記錄總量大到讀不動 → 觸發延後項目 B，不在本次處理。
- `research` 區塊缺失（非首選層）→ 正常情況，不視為錯誤。

## 測試

以 2026-09-16 小倉執行作為 replay fixture：backfill 後的 16 筆 + 本次 14 家候選，
檢查兩件事：

1. agent 有明確寫出「酒類這群只有 N 筆目擊」；
2. **「自家製造・自家調達」不再開火**——本次它開了火，且命中最強的兩家使用者都沒選，
   所以它是現成的回歸案例。

第二個 fixture 由下一次真實執行產生，用來檢查 `rank_shown` / `verdict` 落差是否
真的被 agent 使用。

## 延後項目

**B — 店種側寫卡快取。** 定期把 `sightings.jsonl` 蒸餾成
`profile-酒類.md`、`profile-咖啡.md` 等，每次只讀相關那張卡加該群原始紀錄。
規模大時較省 context，代價是多一個快取失效問題。目前僅 16 筆目擊，屬 YAGNI；
等 log 真的塞不進 context 再做。

## 風險

1. **每次推論可能不一致。** 同樣資料兩次推論可能給出不同的軸。緩解：強制在
   「排序依據」印出軸與計數，讓漂移可見；不追求消除。
2. **冷啟動。** 新店種只有 2–3 筆目擊時推論很薄。緩解：< 5 筆強制宣告薄弱、
   退回中性排序、且無刷掉權。
3. **刷掉權從人工記帳改為當下判斷。** 緩解：證據門檻原封保留，加上筆記內逐條
   交代證據筆數與「若推錯請告訴我」。
4. **失去人類可讀的偏好摘要。** 現行四個桶雖然會誤用，但一眼就能看懂。
   緩解：`preferences.md` 仍在，使用者可自行寫下想固定的結論；skill 每次執行也會在
   「排序依據」印出當次推論出的軸，那是比靜態桶更貼近實際行為的摘要。
